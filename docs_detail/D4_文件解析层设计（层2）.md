# D4 文件解析层设计（对应 2.7.1 层 2：提取与结构化）

**范围**：仅解析层。输入是本地文件路径（模拟 MinIO 取出的原始文件），输出是同名的 `.md` + `_manifest.json`。不包含格式/大小/配额校验（层 1）、分片向量化（层 3）、任务指派逻辑。

**不做的事**：音频（归 D3）、.zip/.rar 等二期格式、chunk 相关字段。

---

## 1. 技术栈

- Python 3.12，用 uv 固定虚拟环境（`uv venv --python 3.12`）。
- 原因：PaddlePaddle 官方 wheel 只覆盖到 3.12，系统默认 Python 3.14 装不上；3.13 支持还在 PaddlePaddle 官方推进中（[PaddlePaddle/Paddle#71616](https://github.com/PaddlePaddle/Paddle/issues/71616)）。
- 接口合约文档（D4_一期架构与接口合约.md 5.1）里 file-service 目录是 `.ts`，属于遗留写法，与 §2.7.4/§6.3 指定的 Python 解析库（pdfplumber、python-docx、openpyxl、OCR）冲突。已确认：解析层用 Python 写，TS 侧后续通过子进程或独立微服务对接，不在本设计范围内。docx/doc 解析引擎后续换成 Pandoc（见 §4），python-docx 降级为兜底手段，不影响这里的结论。

## 2. 模块结构

```
file_parsing/
├── __init__.py
├── types.py          # ParsedResult、ParseError 等公共数据结构
├── detector.py        # detect_format(): 扩展名 + 字节签名 → 规范化类型
├── registry.py         # PARSERS 表 + register() 装饰器
├── source.py           # FileSource 协议，现在只有 LocalFileSource
├── writer.py           # write_output(): 写 .md + _manifest.json
├── ocr_engine.py        # PaddleOCR 单例封装（lazy init）
├── pipeline.py          # parse_file(): 顶层入口
└── parsers/
    ├── __init__.py      # 导入各 parser 模块，触发注册
    ├── text_parser.py   # .txt / .md
    ├── docx_parser.py   # .docx，薄封装，调用 _docx_pandoc.convert_docx_to_markdown()
    ├── doc_parser.py    # .doc，先 LibreOffice 转 .docx，再调用 _docx_pandoc.convert_docx_to_markdown()
    ├── _docx_pandoc.py  # docx/doc 共用：Pandoc 转 markdown，失败降级 python-docx；不注册到 PARSERS，只被上面两个 parser 调用
    ├── xlsx_parser.py   # .xlsx
    ├── pdf_parser.py    # .pdf（pdfplumber，失败页转 OCR）
    └── image_parser.py  # .png / .jpg（OCR）
```

**解耦关系**：
- `detector.py` 只产出类型字符串（如 `"pdf"`），不知道有哪些 parser。
- 各 `parsers/*.py` 只关心"给路径，吐 `ParsedResult`"，不知道自己怎么被调度、不知道输出写到哪。
- `registry.py` 是一张 `dict[str, Callable]`，`pipeline.py` 里调度是 `PARSERS[detected_type](path)` 一行，没有 `if/elif` 链。
- 新增格式 = 新增一个 `parsers/xxx_parser.py`（用 `@register("xxx")` 装饰）+ `parsers/__init__.py` 里加一行 import。`detector`/`registry`/`pipeline`/`writer` 都不改。
- `_docx_pandoc.py` 不是 parser，不用 `@register` 装饰，不进 `PARSERS` 表。docx 和 doc 转完格式后共用同一套"转 markdown"逻辑，抽成内部模块避免重复；`docx_parser.py`/`doc_parser.py` 各自只做格式相关的前置步骤（doc 多一步 LibreOffice 转换），再调用它拿 `(markdown, parser_used)`，包装成 `ParsedResult`。
- `source.py` 的 `FileSource` 协议现在只有 `LocalFileSource`（模拟路径），D2 团队的文件查询接口（入参 file_id，出参二进制流）到位后加 `RemoteFileSource` 实现即可，`pipeline` 不用改。

## 3. 格式检测（detector.py）

不用 `python-magic`/libmagic。原因：Windows 下需要额外装 `python-magic-bin` 或 `python-magic-win64` 才能拿到 libmagic 二进制，历史上有维护空窗；Linux 下虽然 `apt install libmagic1` 就好，但两平台多一层系统依赖排查成本。我们只需覆盖 6 种已知格式，手写字节签名表即可，两平台行为完全一致，纯标准库实现。

```python
SIGNATURES: dict[str, bytes] = {
    "pdf": b"%PDF",
    "png": b"\x89PNG\r\n\x1a\n",
    "jpg": b"\xff\xd8\xff",
    "zip_based": b"PK\x03\x04",   # docx/xlsx 底层都是 zip 容器
    "ole2": b"\xd0\xcf\x11\xe0\xa1\xb1\x1a\xe1",   # 老式 .doc/.xls/.ppt 底层都是 OLE2 复合文档容器
}
```

- `.txt`/`.md`：无固定签名，按扩展名 + 能否 UTF-8/GBK 解码判定。
- `.docx`/`.xlsx`：先命中 `zip_based` 签名，再用标准库 `zipfile` 打开，看内部是否含 `word/document.xml`（docx）或 `xl/workbook.xml`（xlsx）来精确区分。这一步逻辑封装在 `detector.py` 内部，不暴露给 parser 层。
- `.doc`：先命中 `ole2` 签名，再用 `olefile` 打开，看容器内是否存在 `WordDocument` 这个 stream 来判定是不是 Word 文档（而不是同为 OLE2 容器的 `.xls`/`.ppt`）。没有 `WordDocument` stream 时返回 `None`，`.xls`/`.ppt` 走到这一步会被判定为不支持，符合"不做的事"里排除的二期格式边界，不需要额外排除逻辑。
- 扩展名和签名不一致时，以签名判定结果为准（防止企微通用 MIME 类型或伪造扩展名误导）。
- 不在支持列表内的类型，`detect_format` 返回 `None`，pipeline 直接判定不支持，不进入 `registry` 查找。

## 4. 解析器（parsers/）

| 格式 | 工具 | 降级路径 |
|---|---|---|
| .txt / .md | 直接读文本 | 无 |
| .docx | Pandoc（失败降级 python-docx） | Pandoc 转 markdown 失败（找不到可执行文件或退出码非零）→ 降级读 `word/document.xml` 提取段落+表格（python-docx 逻辑）；两级都失败，异常向外抛出，由 `pipeline.py` 判定整体 `failed`（不在 parser 内吞成 failed） |
| .doc | LibreOffice 转 docx → 同上（Pandoc/python-docx） | 先转格式，LibreOffice 转换失败即抛出；转换成功后与 `.docx` 走同一条 Pandoc→python-docx 降级路径 |
| .xlsx | openpyxl | 无 |
| .pdf | pdfplumber，失败转 PaddleOCR | 单页 pdfplumber 失败 → 该页转 OCR；OCR 也失败才记该页为 error；全部页失败才判定整体 `failed` |
| .png / .jpg | PaddleOCR | 无 |

**docx/doc 解析（`_docx_pandoc.py`）**：原方案用 python-docx 直接读 `word/document.xml` 的段落和表格，丢失标题层级、列表、字体样式等结构信息，转成 markdown 后下游可用性差。换成 Pandoc 后可以拿到语义完整的 markdown（标题层级、列表、表格都保留），python-docx 保留下来作为 Pandoc 不可用时的降级手段。

`convert_docx_to_markdown(path: Path) -> tuple[str, str]` 是 docx/doc 共用的核心函数：

```python
def _find_pandoc() -> str:
    configured = os.environ.get("PANDOC_PATH")
    if configured:
        return configured
    found = shutil.which("pandoc")
    if found:
        return found
    raise RuntimeError(
        "找不到 Pandoc 可执行文件，"
        "请设置环境变量 PANDOC_PATH 指向 pandoc(.exe) 路径，或将其加入 PATH"
    )


def convert_docx_to_markdown(path: Path) -> tuple[str, str]:
    try:
        pandoc_exe = _find_pandoc()
        result = subprocess.run(
            [pandoc_exe, str(path), "-t", "gfm", "--wrap=none"],
            capture_output=True,
            check=True,
        )
        return result.stdout.decode("utf-8"), "pandoc"
    except (RuntimeError, subprocess.CalledProcessError, FileNotFoundError):
        return _extract_with_python_docx(path), "python_docx_fallback"
```

- `_find_pandoc()` 与 `doc_parser.py` 里现有的 `_find_soffice()` 完全同构：环境变量 `PANDOC_PATH` 优先，其次 `shutil.which("pandoc")`，都找不到抛出 `RuntimeError` 提示配置方式，不让底层 `FileNotFoundError` 裸抛出。
- Pandoc 输出直接吃 `subprocess` 的 stdout，不落临时文件（`-t gfm --wrap=none` 保证输出是 GitHub 风格 markdown 且不做自动换行折断）。
- 捕获的异常有三种来源：`RuntimeError`（`_find_pandoc()` 找不到可执行文件）、`subprocess.CalledProcessError`（`check=True` 下 Pandoc 退出码非零）、`FileNotFoundError`（`PANDOC_PATH` 指向一个不存在的路径，`subprocess.run` 直接抛这个，`_find_pandoc()` 不校验路径真实存在）。三者都捕获后降级到 python-docx（读 `word/document.xml` 的段落 + 表格，即原有提取逻辑），降级成功仍是整体 `status="success"`，只是 `parser_used` 变成 `"python_docx_fallback"`。
- Pandoc 和 python-docx 降级都失败，异常在这一层不吞，自然向外抛出，和 PDF 之外其他 parser 的"无降级、异常自然抛出"模式一致，由 `pipeline.py` 判定整体 `status="failed"`。
- `docx_parser.py` 直接对本地 `.docx` 路径调用 `convert_docx_to_markdown()`；`doc_parser.py` 先用 LibreOffice 把 `.doc` 转成临时 `.docx`，再调用同一个函数，两者共用同一条 Pandoc/python-docx 降级路径，转换来源不再单独区分标记。

**PDF 页级容错**（用户明确要求："部分页缺失出错也继续解析，最后在 json 中记录情况即可"），三级降级，每页独立走完才算数：

```python
pages_result = []
page_errors = []
for i, page in enumerate(pdf.pages):
    try:
        text = extract_page(page)          # 第一级：pdfplumber 直接抽文本
    except Exception:
        try:
            text = ocr_page(page)          # 第二级：pdfplumber 失败，该页转 PaddleOCR
        except Exception as e:
            page_errors.append({"page": i, "error": str(e)})   # 第三级：OCR 也失败，才记为该页 error
            text = None
    pages_result.append((i, text))   # 占位，保持页序，text 为 None 时输出 [Page N: 解析失败]
```

- 只有 pdfplumber 和 OCR 两级都失败，才算该页失败。两级都失败通常说明问题不在"这页是文字还是扫描图"，而是这页本身的数据有问题（比如页对象被截断、渲染成图片时尺寸异常、OCR 引擎内部报错），这类问题 OCR 也无法绕过。
- 这里讨论的失败是"处理手段跑不通"，不是"文件物理损坏"。若 PDF 结构本身损坏导致 `pdf.pages` 遍历前打开文件就失败，属于文件级问题，在进入逐页循环之前就会判定整体 `failed`，不会走到这里的页级逻辑。
- 整体状态新增 `"partial_success"`，与 `"success"`/`"failed"` 并列。只有全部页都失败才是 `"failed"`。
- 缺失页在 markdown 中用 `[Page N: 解析失败]` 占位，保持页序不断裂。
- `manifest.extraction.page_errors: [{page, error}]` 记录细节，供后续 Agent 或人工判断这几页是否关键。
- `partial_success` 目前只对 PDF 有意义（docx/xlsx/图片是单体解析，没有"部分页"概念），不推广到其他 parser。

**OCR 引擎**：PaddleOCR，`ocr_engine.py` 做成进程内单例（lazy init，第一次调用才加载模型），`image_parser.py` 和 `pdf_parser.py` 的降级分支共用同一个实例，避免重复初始化。

## 5. 输出

- 命名规则：原文件名去扩展名 + `.md` / `_manifest.json`。例：`xx.pdf` → `xx.md`、`xx_manifest.json`。
- 输出目录：本阶段先落到本地 `./parsed_output/`（讨论期约定，非生产路径，后续替换 `writer.py` 内部实现即可，不影响其他模块）。
- 解析失败（非 PDF 的部分页场景，是整体失败）：不写 `.md`，仍写 `_manifest.json`，`status = "failed"` + 错误详情。

**manifest 最小字段**（区别于 §2.7.6 全量 schema，这里只做解析层，不含 ingestion/chunk 字段）：

```json
{
  "source_filename": "xx.pdf",
  "detected_type": "pdf",
  "parser_used": "pdf_direct",
  "status": "success" | "partial_success" | "failed",
  "warnings": [],
  "page_errors": [],
  "parsed_at": "2026-09-21T10:30:00Z"
}
```

**`parser_used` 取值集合**：

| 取值 | 产生场景 |
|---|---|
| `text_direct` | text_parser 直接读文本 |
| `pandoc` | docx 或 doc（转完 docx 后）用 Pandoc 转换成功 |
| `python_docx_fallback` | docx 或 doc，Pandoc 失败后降级 python-docx 成功 |
| `pdf_direct` | pdf 逐页 pdfplumber 成功 |
| ...（OCR、pdf 页级降级等取值见各自 parser，不在此重复列出） | |

`libreoffice_docx` 已废弃，不再产生：这是本次改动前 `doc_parser.py` 的标记，当时 `.doc` 转完 `.docx` 后单独走 python-docx 直接提取。现在 `.doc` 转完 `.docx` 后与原生 `.docx` 共用同一条 Pandoc/python-docx 降级路径（见 §4 docx/doc 解析），不再单独区分"是不是从 doc 转过来的"，历史 manifest 里可能仍有这个值，但新解析不会再产生。

## 6. 环境搭建

```bash
uv venv --python 3.12
uv pip install pdfplumber python-docx openpyxl paddlepaddle paddleocr Pillow
```

- 当前 Windows 本地开发测试，未来迁移 Linux 部署。
- 迁移到 Linux 时用相同的 `uv venv --python 3.12`；若目标机器上 PaddlePaddle 3.12 wheel 装不上，是 PaddlePaddle 那层的问题，不影响 `detector.py`（纯标准库，无平台依赖）。

**系统级二进制依赖**：Pandoc 和 LibreOffice 都不是 Python 包，`uv pip install` 装不到，需要在目标机器上单独安装：

- **Pandoc**：docx/doc 解析走 Pandoc 转 markdown（见 §4）。装好后默认应在 `PATH` 里，找不到时通过环境变量 `PANDOC_PATH` 指定可执行文件路径。
- **LibreOffice**：`.doc` 解析先转 `.docx`（见 §4），依赖 `soffice` 可执行文件。同样默认从 `PATH` 找，找不到时通过环境变量 `LIBREOFFICE_PATH` 指定路径。
- 两者都缺失或路径配置错误时，对应 parser 会抛出清晰的 `RuntimeError` 提示如何配置，不会裸抛 `FileNotFoundError`。
- 迁移到 Linux 部署时，这两个二进制依赖同样需要单独安装（如 `apt install pandoc libreoffice`），不随 `uv venv` 走。
